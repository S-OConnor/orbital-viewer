🛰 Orbital LOS Viewer

Project Overview

This page gives decision makers and newcomers everything needed to understand what Orbital LOS Viewer is, why it exists, and how it is put together — without reading a line of code.

Executive summary

Orbital LOS Viewer (OLV) is a small, self-contained software stack that visualizes a primary satellite in Earth orbit plus up to 5,000 tracked objects — orbital debris, stars, comets, other satellites, and hot ground objects — live in a web browser. All positions are Earth-Centered Earth-Fixed (ECEF) meters, updated at a nominal 1 Hz.

The stack has three components connected by two well-specified protocols:

  1. olv_sim — a C++ command-line simulator that replays CSV mission files or synthesizes deterministic load-test data, emitting binary UDP.
  2. olv_backend — a C++20 server (Boost.Asio/Beast) that validates and aggregates incoming track data and rebroadcasts a world-state snapshot as WebSocket JSON.
  3. Frontend — a dependency-free, framework-free HTML/CSS/JS application with a custom minimal WebGL renderer. No build step, no npm packages.

Version: 0.1.0 (CMake project version), with additive frontend feature versions v0.3 (satellite POV view) and v0.4 (celestial sky), plus a completed boot-selectable input-source feature adding IEEE 1278.1 DIS ingest. License: MIT. Deployment scope: trusted localhost/LAN only — no TLS or authentication, by explicit design.

The problem being solved

Situational-awareness tooling for orbital scenarios typically demands heavyweight stacks: GIS frameworks, message brokers, GPU engines, or cloud services. OLV solves a deliberately scoped version of the problem: display a live, validated track picture from a local data source in any modern browser, on an air-gapped or LAN-only network, with a codebase small enough for one team to audit end-to-end.

Key constraints the design answers:

  • No runtime internet access. All assets (including NASA Earth imagery and the star catalog) are vendored or first-party; nothing is fetched at runtime.
  • Untrusted input tolerance. Every inbound datagram passes an ordered validation pipeline (structure, CRC-32, NaN/Inf, coordinate range, sequence staleness) before touching shared state.
  • Minimal third-party surface. Runtime dependencies are exactly two: header-only Boost (Asio/Beast) and the pinned, checksum-verified open-dis-cpp v1.2.0 static library. The frontend ships zero third-party code.
  • Interoperability. Besides its first-party OLV1 protocol, the backend can ingest standard IEEE 1278.1 DIS Entity State PDUs, so it can sit on an existing simulation exercise network.

Major capabilities

  • Live 3D display of one primary satellite and up to 5,000 tracked objects at 1 Hz, in ECEF meters, on a textured, sun-lit Earth globe (vendored NASA Blue Marble day / Black Marble night imagery).
  • Five object categories, each with distinct color, size, and icon: debris, star, comet, satellite, ground-hot.
  • Two view modes: a free orbit camera, and a satellite point-of-view mode — a 170° equidistant-fisheye nadir view from the primary satellite, toggled with V.
  • Time-accurate celestial background (optional): ~230 brightest stars, the Moon with illuminated-fraction readout, and the five naked-eye planets — all positioned from the state message's serverTime.
  • Per-object trails (0–60 s, age-faded), on-screen labels (capped for readability), filterable object list, satellite telemetry, connection status, and live UDP/WebSocket statistics panels.
  • Two ingest protocols, chosen at backend boot: first-party OLV1 binary UDP (default) or IEEE 1278.1 DIS Entity State PDUs.
  • Simulation tooling: CSV mission replay (with looping) and deterministic seeded synthetic generation for load testing, over either wire protocol.
  • Operations tooling: one-command containerized bring-up (scripts/run_all.sh), plain-text audit log, CycloneDX SBOM generation, end-to-end integration test.

High-level architecture

Data flows one way, through three processes:

Inside the backend there are exactly two threads: an input thread (the boot-selected input source — OLV1 or DIS) that decodes and validates datagrams, and the main thread that runs the WebSocket server and a 1 Hz broadcast timer. They share exactly one mutex-protected StateStore. See Architecture at a Glance and the detailed architecture.

Design philosophy

  • Simplicity over maximum performance. 5,000 objects at 1 Hz fits comfortably in one GL_POINTS draw call and a ~450 KB JSON message on a LAN; the design refuses complexity that this workload doesn't need.
  • Frozen interfaces first. Wire protocols and module APIs were specified and frozen (in docs/PLAN.md and the protocol docs) before implementation; the checked-in specs are normative.
  • Dependency minimalism. A first-party TOML-subset parser, a first-party ~120-line C++ test framework, and a first-party WebGL renderer exist precisely so the repo doesn't need toml++, Catch2, or Three.js.
  • Fail fast, fail loud. Backend/simulator configuration is strict — an unknown key or out-of-range value aborts startup with the offending key and line. The frontend is deliberately lenient — a bad config.toml warns and falls back to defaults so a deployment mistake never bricks the page.
  • Determinism. Synthetic data generation is seeded (never time-based), the example CSV is regenerable from a fixed seed, and SBOM serial numbers are content-derived — runs and artifacts are reproducible.

Deployment overview

Two supported deployment shapes, both localhost/LAN-scoped:

  • Containers (recommended for demos/ops): three OCI images — backend and simulator built from containers/Containerfile.cpp (Debian bookworm-slim, non-root UID 10001), frontend from containers/Containerfile.frontend (nginx:alpine-slim) — orchestrated by containers/compose.yaml under Podman or Docker. Host ports are remappable via OLV_HTTP_PORT/OLV_WS_PORT/OLV_UDP_PORT.
  • Native binaries: build with CMake, run the two executables directly, and serve frontend/ with any static file server (it must be HTTP, not file://, because the frontend uses ES modules).

Default ports: 47000/udp (OLV1 ingest), 47001/udp (DIS ingest), 8765/tcp (WebSocket), 8000/tcp (HTTP, dev server/containers). See Best Practices for firewall and deployment guidance.

Example use cases

  • Exercise wall display: point olv_backend --input-mode dis at an existing DIS exercise network; entities appear as categorized tracks with the configured entity promoted to the primary-satellite telemetry panel.
  • Mission playback: convert recorded ephemerides to the mission CSV format and replay them at 1 Hz (or faster) for after-action review.
  • Pipeline soak testing: olv_sim --generate 5000 --duration 0 drives the full validation/broadcast path at maximum object count indefinitely, with live drop/rate counters in the UI.
  • Teaching aid: the sky feature places the real Moon, planets, and bright stars for any timestamp; the sat-view mode shows what a nadir-pointing LEO camera would geometrically see.

Major interfaces

  • OLV1 UDP protocol — little-endian binary datagrams, 56-byte header + 48-byte object records + CRC-32; max 6,204 bytes.
  • DIS input — IEEE 1278.1 Entity State PDUs (versions 5–7, big-endian), mapped deterministically into the same internal model.
  • WebSocket JSON — a hello message on connect, then state snapshots at 1 Hz with row-array object encoding.
  • File formats — mission CSV, the strict TOML subset used by all three configs, and the backend log line format.
