Data flow, step by step

  1. Source: olv_sim produces one frame per update cycle (satellite state + object list). CSV rows sharing a time_s value form one frame; in generate mode, frames are computed analytically from circular-orbit math.
  2. Chunking: in OLV1/DIS mode, frames are split into packets of at most 128 objects (kMaxObjectsPerPacket); each packet is self-contained and carries the satellite state plus object_total, so packet loss never corrupts state. In OLV2 mode, chunking is per track instead of per frame: each datagram carries one track's next 1–25 new, time-stamped points (olv2_points); batches for different tracks are independent and a sender never resends a point.
  3. Transport: packets go out as UDP datagrams — OLV1 (little-endian, CRC-32 trailer, port 47000), DIS Entity State PDUs (big-endian, one PDU per datagram, port 47001), or OLV2 per-track batches (little-endian, CRC-32 trailer, port 47002).
  4. Validation: the backend's input thread runs the full ordered validation pipeline; any failure drops the entire packet, increments a per-reason counter, and is logged. Nothing is partially applied.
  5. State merge: accepted packets upsert objects by id. OLV1/DIS packets replace the satellite state wholesale; OLV2 replaces it only when the packet's newest point is newer than the sample already stored, since datagrams for different tracks interleave. OLV2 additionally forwards every accepted point to clients once as trailPoints. Objects not refreshed within the expiry window (default 15 s) are pruned at snapshot time.
  6. Broadcast: every second (configurable up to 60 Hz) the main thread takes a snapshot copy, serializes it once, and enqueues the shared string to every connected WebSocket session. Slow clients drop frames (never the connection) beyond a 5-frame outbox.
  7. Render: the browser parses and validates each state message, stores the latest snapshot, and renders continuously at display refresh rate, interpolating the scene clock from serverTime for Sun/Moon/planet/ star positions and, for ids with trailPoints, drawing server-fed trails at source sample rate instead of the 1 Hz client-built default.

Threading model (summary)

  • Backend, thread 1 — input. Owned by the boot-selected InputSource; runs a private io_context and an async UDP receive loop. Writes to StateStore only through countReceived / countDropped / apply.
  • Backend, thread 2 — main. Runs the WebSocket acceptor, all sessions, and the broadcast timer on one io_context. Sessions are single-threaded by construction — no session locking exists or is needed.
  • The only lock in the system is the single std::mutex inside StateStore; snapshot() returns a full copy so the broadcast path never holds the lock while serializing.
  • Frontend is single-threaded JavaScript: a requestAnimationFrame render loop, a WebSocket message handler, and a 1 s UI tick.

Notable architecture decisions

  • Custom WebGL renderer, no Three.js — the scene is one sphere, a graticule, one points draw, line trails, and a 2D overlay; a framework would dominate the dependency budget for little gain. The renderer API is engine-agnostic, so swapping later is localized to renderer.js.
  • Row-array JSON — object rows are 11-element arrays, roughly halving message size versus key/value objects at 5,000 objects (~450 KB vs ~800 KB per broadcast).
  • Per-protocol staleness, receiver-stamped arrival time — the backend always stamps its own arrival time (it drives lastDataTime and object expiry). Stale/duplicate rejection is protocol-specific: OLV1 carries no wire timestamps and uses a wraparound-safe signed-difference check on the packet sequence; DIS compares per-entity PDU timestamps; OLV2 compares each track's first point time against the newest point already accepted for that track.
  • Pluggable input source at one seam — the OLV1, DIS, and OLV2 paths are strategy implementations behind the InputSource interface; everything downstream of StateStore is identical across all three modes (OLV2 additionally populates the trail buffer that snapshot() drains into trailPoints).
  • Loss tolerance without reassembly — each packet independently refreshes the satellite and merges its object chunk by id; there is no multi-packet reassembly state to corrupt.
