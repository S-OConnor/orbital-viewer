Supported platforms, compilers, build systems

  • Operating systems: Linux is the primary target (Debian/Ubuntu, Fedora, and immutable/atomic distros such as Bazzite/Silverblue via Homebrew/Linuxbrew are documented). The integration test and container scripts are POSIX/UNIX-only (the CMake integration test registers only on UNIX). Any OS with a modern browser can act as a frontend client.
  • Compilers: GCC ≥ 12 or Clang ≥ 14 (per THIRD_PARTY.md); any C++20-conforming compiler should work.
  • Build system: CMake ≥ 3.20 with the default generator (Makefiles or Ninja). Build type defaults to Release when unspecified.
  • Browsers: any modern browser with WebGL 1 and ES-module support. The page must be served over HTTP (ES modules are blocked from file://).
Assumption: Windows and macOS native builds are not exercised by any script or test in the repository. The code is portable C++/Boost, so they may work, but treat them as unsupported until verified.

Vendored assets (public domain, NASA Media Usage Guidelines): frontend/assets/earth_day.jpg (Blue Marble: Next Generation, Dec 2004) and frontend/assets/earth_night.jpg (Black Marble / Suomi NPP VIIRS, 2012). SHA-256 hashes are recorded in frontend/assets/README.md and tracked as file-type components in the frontend SBOM. The ~200-entry bright-star catalog is first-party data hardcoded in frontend/js/star_catalog.js, not an asset file.

SBOMs: sbom/ holds hand-maintained, committed CycloneDX 1.5 JSON for the backend (the olv-builder image's Boost version and the open-dis-cpp pin) and the frontend (zero code components + the two image assets with their SHA-256). Strategy: docs/SBOM.md; full license table: THIRD_PARTY.md.

Air-gap posture

  • Runtime: no component makes any outbound network call. The frontend serves everything from its own origin.
  • Native build: needs only a system Boost and a C++20 toolchain, plus a one-time open-dis-cpp install from a mirrored copy of the pinned tarball, following the step in containers/Dockerfile.builder.
  • Container build: build (or pull from an internal registry) the olv-builder image once on a connected machine — needs a dnf mirror and the open-dis-cpp tarball (or a mirror URL as a build arg). Offline machines then only need olv-builder and a mirrored rockylinux:10.2-minimal runtime image; scripts/build.sh, scripts/test.sh, and scripts/package.sh (which builds containers/Dockerfile.backend/Dockerfile.simulator) all run with --network none; see containers/Dockerfile.builder for exact commands.

CI/CD status

Gap: the repository contains no CI/CD configuration (no GitHub Actions, GitLab CI, or similar). All quality gates — ctest, Node tests, format-check, lint, the integration test — exist as local commands and are run manually. Wiring them into a pipeline is a natural first infrastructure task; the commands are already non-interactive and exit-code clean. See Testing for the full list.
