Formatting is enforced by tools; conventions are enforced by review. Both are described here.

Code organization rules

  • Shared wire/parsing code is header-only under include/olv/ and consumed via the olv_proto target — never duplicated.
  • Testability drives structure: simulator logic lives in olv_sim_lib (main.cpp is thin); frontend pure logic is import-safe (no DOM at import time); network-touching code gets injectable seams (wsFactory, processDatagram).
  • One owner per concern: DOM only in main.js/ui.js; GL only in the renderer cluster; the mutex only in StateStore.
  • Third-party isolation: open-dis-cpp headers are SYSTEM includes; its types don't leak past dis_input_source.cpp / dis_builder.cpp.
  • No exceptions for control flow: parse/validation paths return error enums or result structs; exceptions are reserved for constructor-time resource failures and third-party boundaries (caught immediately).

Documentation expectations

  • Specs are normative and updated first. Wire-format changes edit docs/PROTOCOL_*.md together with the code; each spec names its reference implementation, which wins on conflict.
  • Nontrivial features start as a frozen interface doc in docs/features/ (see FEATURE_SATVIEW / FEATURE_SKY / FEATURE_INPUT_SOURCES as templates) — module APIs, constants, and behavior are agreed before implementation.
  • Comments state constraints, not narration. The codebase's best examples: the TOML grammar block in toml.hpp, the LOCKSTEP warning in renderer.js/sat_camera.js, the carry-forward note in state_store.cpp. Follow that register.
  • Config keys are documented in the sample TOML files — a new key isn't done until config/*.toml shows it commented with its default.

Review checklist

No CI exists, so review carries the enforcement load. Before approving:

  1. cmake --build build-docker --target format-check lint (inside olv-builder) — clean.
  2. ctest --test-dir build-docker --output-on-failure (inside olv-builder) and node --test "frontend/tests/*.test.mjs" (host) — green, including integration.
  3. New behavior has tests at the right layer (unit for logic, integration for cross-component contracts).
  4. Wire/config/API changes updated the normative docs and sample configs.
  5. The five invariants hold (see Extending): all-or-nothing drops, counted+logged drops, StateStore-only writes from thread 1, GLSL/JS fisheye lockstep, strict-backend/lenient-frontend config.
  6. No new third-party dependency without an explicit decision (update THIRD_PARTY.md, SBOM generator, and the air-gap notes if one is truly needed).
