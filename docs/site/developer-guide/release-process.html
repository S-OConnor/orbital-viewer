Release Process

The repository has no formal release automation yet; this page documents the versioning scheme actually in use, the manual release workflow the repo's tooling supports today, and the assumptions involved.

Versioning

  • Project version: 0.1.0, declared in the top-level CMakeLists.txt (project(orbital_los_viewer VERSION 0.1.0)) and mirrored as metadata.component.version in both sbom/*.cdx.json files and the frontend's About text. These three must be bumped together.
  • Protocol versions are independent of the project version: OLV1 wire version 1 (kVersion in protocol.hpp) and WS protocolVersion: 1. They bump only on breaking layout changes; receivers reject unknown versions.
  • Feature versions (v0.3 sat-view, v0.4 sky) label additive frontend feature specs in docs/features/, not releases.
  • Dependency pins: open-dis-cpp v1.2.0 is pinned by URL + SHA-256 (OPEN_DIS_VERSION/OPEN_DIS_SHA256 build args) in containers/Dockerfile.builder and echoed in sbom/backend.cdx.json/THIRD_PARTY.md — a bump touches all three.
Assumption: no git tags or changelog file exist in the repository; the scheme below (semver tags + generated changelog) is the recommended practice, not an established one.

Recommended release workflow

  1. Freeze & verify (see Installation: Building the binaries for the full pipeline): 
    scripts/build.sh
scripts/test.sh
node --test "frontend/tests/*.test.mjs"   # host
# format-check/lint aren't wired into a script — run them the same way
# scripts/build.sh invokes olv-builder (see Build System: Quality targets):
docker run --rm --network none --security-opt label=disable \
  -v "$PWD":/src -w /src localhost/olv-builder:latest \
  cmake --build build/container --target format-check lint
  2. Bump the version in CMakeLists.txt, sbom/*.cdx.json (metadata.component.version, plus metadata.timestamp), and the About text; reconfigure and rebuild. Check the SBOM component versions still match the olv-builder image (see docs/SBOM.md).
  3. Regenerate artifacts: 
    python3 scripts/make_example_csv.py         # only if the CSV contract changed
  4. Changelog: generate from history since the last tag (git log --oneline vPREV..HEAD) and curate by area (backend/simulator/frontend/protocols/docs). Call out any protocol or config changes prominently — they affect interop.
  5. Tag: annotated semver tag, e.g. git tag -a v0.2.0 -m "..."; push the tag.
  6. Build release artifacts: 
    # Build-environment image (only needed again if its inputs changed — toolchain
# packages or the pinned open-dis-cpp version); push it to the internal registry:
podman build -f containers/Dockerfile.builder -t harbor.example.com/olv/olv-builder:v0.2.0 .
podman push harbor.example.com/olv/olv-builder:v0.2.0

# Release binaries, compiled inside that image and staged into build/dist/:
OLV_BUILDER_IMAGE=harbor.example.com/olv/olv-builder:v0.2.0 scripts/build.sh
OLV_BUILDER_IMAGE=harbor.example.com/olv/olv-builder:v0.2.0 scripts/test.sh

# Container images, tagged with the version, wrapping those staged binaries:
OLV_BUILDER_IMAGE=harbor.example.com/olv/olv-builder:v0.2.0 \
OLV_BACKEND_IMAGE=olv-backend:v0.2.0 OLV_SIM_IMAGE=olv-sim:v0.2.0 \
  scripts/package.sh
podman build -f containers/Containerfile.frontend -t olv-frontend:v0.2.0 .
  7. Smoke the release exactly as users run it: scripts/run_all.sh --build, open the page, confirm data flows and the About modal shows the new version.

Packaging & deployment

  • Deliverables: the three container images (preferred), or a tarball of olv_backend + olv_sim + the frontend/ directory + config/ examples + docs/. There is no make install, .deb/.rpm, or registry push script — distribution is manual or site-specific.
  • Ship the SBOMs (sbom/*.cdx.json) alongside artifacts; they are committed, so the tagged commit's copies are the release's.
  • Air-gapped consumers additionally need the pushed olv-builder image and the mirrored runtime base images — include (or point at) them in the release bundle for such sites (see Installation).

Compatibility rules for releases

Settings/localStorage shapeCoerce-with-default pattern means no migration needed for additive keysNone

Toward automated releases

Everything above is scriptable today: configure + build, the three test commands, image builds, and the container smoke test (run_all.sh already waits for readiness and exits non-zero on failure). A CI pipeline that runs the verification block on every commit and the full artifact build on tags would close the repo's main infrastructure gap — see CI/CD status.
