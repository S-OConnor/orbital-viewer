Build System

CMake ≥ 3.20: the top-level CMakeLists.txt sets up the toolchain and options, defines the shared INTERFACE targets, finds dependencies, then adds src/, tools/ and test/, each of which lists its own sources and target options, before defining the format/format-check/lint targets at the bottom. There is no separate cmake/ directory — tools/simulator/ inlines its own minimal copy of the same settings so it stays independently configurable. The frontend has no build step at all. The commands on this page assume the CMake configure/build happens inside the olv-builder container image (containers/Dockerfile.builder) via docker run ... cmake ... — see Installation: Building the binaries for the exact invocation; a native toolchain also works (advanced, unsupported) if you already have Boost and an OpenDIS CMake package on CMAKE_PREFIX_PATH.

Target map

Top-level CMakeLists.txt: toolchain, options, shared targets

  • C++20 required, extensions off; CMAKE_BUILD_TYPE defaults to Release when unset.
  • Options: OLV_BUILD_TESTS (default ON — builds test binaries and calls enable_testing()) and OLV_WERROR (default OFF).
  • Homebrew handling: appends $HOMEBREW_PREFIX (or /home/linuxbrew/.linuxbrew) to CMAKE_PREFIX_PATH — this is why Bazzite/Silverblue builds usually work with no extra flags.
  • INTERFACE targets: olv_proto (adds include), olv_test_support (adds test/support), olv_warnings (-Wall -Wextra -Wpedantic [+ -Werror]).
  • tools/simulator/CMakeLists.txt inlines its own copy of this block under if(NOT DEFINED PROJECT_NAME), so it works standalone too.

find_package(OpenDIS)

The top-level CMakeLists.txt locates the package installed by scripts/install_open_dis.sh with upstream's own CMake package config: find_package(OpenDIS 1.2 REQUIRED CONFIG), then links OpenDIS::OpenDIS6. CMake's normal CONFIG-mode search finds it automatically in /usr/local, and in ~/.local when ~/.local/bin is on PATH (CMake's PATH-derived prefix search); any other install location needs -DCMAKE_PREFIX_PATH=DIR or -DOpenDIS_DIR=DIR/lib64/cmake/OpenDIS. There is no custom find-module anymore — imported-target headers are marked SYSTEM automatically (so upstream-generated code doesn't trip our warning set), and a missing package fails configure with CMake's own standard find_package error, which names the package and the search paths tried.

Subproject layout

  • CMakeLists.txt (top level) — project(), sets the toolchain/options and shared INTERFACE targets, finds dependencies (Threads, find_package(Boost 1.74 REQUIRED CONFIG) — CONFIG mode, required by CMake 4-era Boost packages, header-only usage — and find_package(OpenDIS 1.2 REQUIRED CONFIG)), adds the subdirectories below, and defines the format/format-check/lint targets at the bottom.
  • src/CMakeLists.txt — static libs olv_core and olv_net, and the olv_backend executable.
  • tools/CMakeLists.txt — the olv_ws_probe tool, then add_subdirectory(simulator).
  • test/CMakeLists.txt (only when OLV_BUILD_TESTS) — olv_backend_tests (CTest backend_unit) and the integration test (UNIX only): runs scripts/integration_test.sh with the three target file paths, 120 s timeout, label integration.
  • olv_backend, olv_ws_probe and olv_backend_tests set RUNTIME_OUTPUT_DIRECTORY to the build root, so they still land at <build-dir>/olv_backend etc. (build-docker/ in the documented container workflow); olv_sim lands in <build-dir>/tools/simulator/.
  • tools/simulator/CMakeLists.txt — olv_sim_lib static lib (everything except main.cpp, so tests link the real code), olv_sim, and olv_sim_tests (CTest sim_unit).
  • tools/simulator/CMakeLists.txt begins with an if(NOT DEFINED PROJECT_NAME) standalone header — you can configure the simulator in isolation, e.g. inside the container: docker run --rm -v "$PWD":/src -w /src localhost/olv-builder:latest cmake -S tools/simulator -B build-sim; in that mode it finds Threads, Boost and open-dis-cpp itself.

Quality targets

cmake --build build-docker --target format         # clang-format -i over include/src/test/tools
cmake --build build-docker --target format-check   # --dry-run --Werror (CI-suitable)
cmake --build build-docker --target lint           # cppcheck warning/performance/portability, exit 1 on findings

(run each via docker run --rm -v "$PWD":/src -w /src localhost/olv-builder:latest sh -c '...', as in Installation). Both no-op with a notice if the tool isn't installed — neither clang-format nor cppcheck are in the olv-builder image today; add them to a derived image, or run these targets from a native build, for real output. The format targets also carry a Homebrew keg-only HINT path so brew-installed clang-format is found on a native build. clang-tidy is configured (.clang-tidy) but not wired into a target — it needs a compilation database and a native toolchain to run it via your IDE or manually (advanced):

cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
clang-tidy -p build src/*.cpp tools/simulator/src/*.cpp

Dependency management

  • Boost: system-provided, never vendored (size). Header-only usage means no Boost link libraries and no Boost ABI concerns.
  • open-dis-cpp: pinned v1.2.0, sha256-verified tarball, built once into a prefix by scripts/install_open_dis.sh using upstream's own CMake project (static, Release, warnings silenced; DIS6 and DIS7 are built because upstream's package config requires both, though only DIS6 is used); installs a CMake package config plus LICENSE + provenance. Consumed via find_package(OpenDIS CONFIG) / OpenDIS::OpenDIS6 — no custom find-module. No package manager (vcpkg/Conan) is used anywhere — deliberate, for air-gap simplicity.
  • Frontend: zero dependencies; no npm, no lockfiles.

CTest & CI integration

ctest --test-dir build-docker --output-on-failure            # all three tests
ctest --test-dir build-docker -R backend_unit                # one suite
ctest --test-dir build-docker -L integration                 # by label

(run inside the container, e.g. docker run --rm -v "$PWD":/src -w /src localhost/olv-builder:latest sh -c 'ctest --test-dir build-docker ...'.)

No CI pipeline exists yet. Everything a pipeline needs is already a clean, non-interactive command, run inside the olv-builder image: cmake --build build-docker --target format-check lint, ctest --test-dir build-docker, plus (on the host) node --test "frontend/tests/*.test.mjs". A minimal CI job is literally those lines after configure — build/pull olv-builder, configure inside it, and run the three checks. See Release Process.

Container builds

Two files now split what used to be one: containers/Dockerfile.builder builds the olv-builder build-environment image — Rocky Linux 10.2 + gcc-c++ cmake make boost-devel, then install_open_dis.sh --prefix /usr/local — meant to be built once on a connected machine and pushed to an internal registry. containers/Dockerfile's build stage is FROM ${OLV_BUILDER_IMAGE} (default localhost/olv-builder:latest) and installs/fetches nothing itself; it COPY . ., configures with -DOLV_BUILD_TESTS=OFF, and builds only olv_backend olv_sim. The backend and simulator runtime targets (backend is the last stage, so it's also the default docker build target) copy a single binary each into ${OLV_RUNTIME_IMAGE} (default rockylinux:10.2-minimal) with a non-root user (UID 10001) — no packages installed at runtime, since Boost is header-only and open-dis is linked statically. compose.yaml has a builder service behind the builder profile so up never builds it implicitly; scripts/run_all.sh builds it first unless OLV_BUILDER_IMAGE is already set. Containerfile.frontend is unchanged: a one-stage nginx:alpine-slim copy of frontend/ and docs/ — no toolchain at all.
