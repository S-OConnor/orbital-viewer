Debugging

Workflows and tools for each layer. User-facing symptom lookup lives in Troubleshooting; this page is the engineer's toolbox.

The general workflow

  1. Localize with the pipeline's own instrumentation first. The Stats panel + backend log tell you which stage is failing: packets not received (network), received-but-dropped (validation — the reason is logged), accepted but not displayed (frontend). Only then reach for a debugger.
  2. Reproduce deterministically. olv_sim --seed N --duration 10 gives an identical packet stream every run; most bugs can be pinned to a seed + timestamp.
  3. Shrink to a unit test. Nearly every seam has a test-friendly entry point: proto::decode on crafted bytes, DisInputSource::processDatagram, parseStateMessage on a captured frame, fisheyeProjectNdc on a single point. Encode the repro as a test before fixing.

Logging & tracing

# Everything the backend does, live:
./build/olv_backend --log-level debug --log-file dbg.log
tail -f dbg.log
# debug level adds: every accepted packet (seq/objs/total/source),
# stale drops, DIS filtered/ignored PDU lines.
  • The logger flushes every line — logs are complete even after a crash.
  • Simulator: watch the per-cycle stdout line; send errors always print with errno text.
  • Frontend: DevTools console shows config warnings and parse errors; connection.getStats() and the parse-error counter are inspectable from the console via the module registry if you expose them, or add temporary logging in net.js's catch block.

Watching the wire

# UDP: is anything arriving? (loopback capture)
sudo tcpdump -i lo -X udp port 47000

# Decode-level check without the backend: any packet whose 4 first bytes
# aren't 4F 4C 56 31 ("OLV1") is not an OLV1 packet.

# WebSocket: capture frames as text
./build/olv_ws_probe --host 127.0.0.1 --port 8765 --count 3 \
    --timeout 10 --out frames.jsonl
python3 -m json.tool <(head -1 frames.jsonl)     # pretty-print the hello
node frontend/tests/validate_message.mjs frames.jsonl   # strict re-parse

Native debugging (gdb/lldb)

cmake -S . -B build-dbg -DCMAKE_BUILD_TYPE=Debug
cmake --build build-dbg -j
gdb --args ./build-dbg/olv_backend --udp-port 47000 --ws-port 8765
  • Remember the thread model: info threads shows the main (WS) thread and the input thread. Useful breakpoints: StateStore::apply (every accepted packet), WsServer's broadcast tick, proto::decode return paths.
  • Deadlock suspicion: there is exactly one application mutex (StateStore::mutex_) — if both threads are stuck, one of them is holding it across something blocking, which the design forbids (snapshot() copies precisely to avoid this).
  • Unit tests are ordinary binaries: gdb ./build-dbg/olv_backend_tests and break on a failing case's function (find names via --list).

Sanitizers

No preconfigured sanitizer build exists; add flags at configure time:

cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer" \
  -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"
cmake --build build-asan -j
ctest --test-dir build-asan --output-on-failure

# Thread races (the StateStore/two-thread contract):
#   use -fsanitize=thread in a separate build tree (TSan and ASan don't mix)

TSan on the integration test is the strongest automated check of the threading model — worth running after any change to state_store, ws_server, or an input source.

Frontend debugging

  • Renderer without a backend: serve the repo root and open frontend/dev/smoke.html — deterministic synthetic scene, all categories, V/S toggles. Ideal for shader and projection work.
  • Pure-module REPL: node can import any pure module directly: const {sunDirectionEcef} = await import('./frontend/js/sun.js') — reproduce math bugs outside the browser.
  • WebGL: browser DevTools + the Spector.js extension (or about:gpu for context issues). The renderer's four programs are named in source (earthProg, lineProg, pointsProg, markerProg); GLSL compile errors are surfaced in the console with the shader source.
  • Fisheye lockstep bugs (objects picking wrong in SAT view, or drawn vs picked positions diverging): compare fisheyeProjectNdc output in Node against what the shader draws for the same world point — the two implementations must match; sat_camera.test.mjs has the harness pattern.
  • State inspection: the app exposes no globals by design; set a breakpoint in main.js's onState callback and inspect the parsed message / model there.

Profiling

# Backend CPU profile under load (perf, Linux)
perf record -g ./build/olv_backend --quiet --log-file /dev/null &
./build/tools/simulator/olv_sim --generate 5000 --rate 4 --duration 30
perf report
# Expect hotspots in json_writer (serialization) and decode/crc32.
  • Frontend: DevTools Performance tab during a 5,000-object + trails run; the known heavy paths are the trail buffer rebuild and label overlay pass.
  • Broadcast cost scales with objectCount × broadcastHz × clients for enqueue, but serialization happens once per tick regardless of client count (shared string) — measure before optimizing.
