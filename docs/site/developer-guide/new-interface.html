Adding a New Interface

The complete, end-to-end procedure for adding a new external interface to the system — most commonly a new input source (a third wire protocol besides OLV1 and DIS), but the same discipline applies to a new output interface. This is the project's designed-for extension point: DIS was added exactly this way, and docs/features/FEATURE_INPUT_SOURCES.md is the historical record of that work.

1. Anatomy of an interface

In this codebase, an "interface" is not just a class — it is a bundle of five artifacts that must ship together:

  1. A protocol specification — a normative docs/PROTOCOL_<NAME>.md defining the accepted wire subset, the mapping into the internal model, the ordered validation list, and the stats accounting identity.
  2. An implementation behind an existing seam — for inputs, a class implementing InputSource; it may use a third-party decoder but must not leak its types past the implementation file.
  3. A configuration surface — strict, flat keys under the relevant TOML table, plus (optionally) a CLI mode flag.
  4. Tests at every layer it touches — unit tests against a socket-free seam, config tests, and (ideally) an integration-test scenario.
  5. Documentation & supply-chain updates — sample configs, README, THIRD_PARTY.md/SBOM if a dependency was added.

2. Write the spec first

Before code, write two documents (this is the repo's frozen-interface process):

  • docs/features/FEATURE_<NAME>.md — the design record: motivation, decisions with rationale, module/config surface, phases, acceptance criteria. Template: FEATURE_INPUT_SOURCES.md.
  • docs/PROTOCOL_<NAME>.md — the normative operator/implementer spec. It must answer, minimum:
    • Transport, byte order, one-message-per-datagram rules.
    • The accepted subset (versions, message kinds) and what happens to everything else (drop-as-malformed vs ignore-as-received).
    • Field-by-field mapping to StatePacket/ObjectRecord, including fixed values for fields your protocol can't express (DIS precedent: confidence=100, intensity=0, flags=HAS_VELOCITY) and any lossy conversions (DIS precedent: id folding, STAR→DEBRIS).
    • How the primary satellite is identified (config-driven, like dis_satellite_entity_id) and whether its state is carried forward.
    • The ordered validation list with a named outcome per step, and the stats identity (received == accepted + malformed + stale, or a documented inequality like DIS's).
    • Staleness semantics, and how the shared OLV1 sequence gate is satisfied (synthesized strictly-increasing sequence is the standard answer).
    • The config keys (§4 below), verbatim, with defaults and ranges.

3. Implement the InputSource

Skeleton for backend/src/foo_input_source.{hpp,cpp}, mirroring DisInputSource:

// foo_input_source.hpp
struct FooInputConfig {
  std::string bind_address = "0.0.0.0";
  int port = 47002;                       // pick an unclaimed default
  // ... protocol-specific keys, defaults matching PROTOCOL_FOO.md §config
};

class FooInputSource : public InputSource {
 public:
  FooInputSource(const FooInputConfig& cfg, StateStore& store, Logger& log);
  void start() override;                  // idempotent: spawn io thread
  void stop() override;                   // idempotent: stop + join

  // PUBLIC TEST SEAM — full pipeline without a live socket:
  void processDatagram(const uint8_t* data, std::size_t len,
                       const boost::asio::ip::udp::endpoint& from);
 private:
  // private io_context + socket + std::thread; carried-forward satellite
  // state; uint32_t seq_ = 0 (synthesized, strictly increasing);
  // per-source staleness bookkeeping.
};

Rules the implementation must follow (these are the invariants every existing source obeys):

  • Own your thread. A private io_context run on an internal std::thread; start()/stop() idempotent; the constructor binds the socket so bad config fails before threads exist.
  • Three calls only. countReceived(len) first for every datagram; then either countDropped(kind) + a log line, or apply(pkt, wall_now, mono_now). Never touch anything else.
  • All-or-nothing. A datagram is fully applied or fully dropped; no partial state.
  • Validate in your spec's order, log every drop with its reason and source address (WARN for malformed, DEBUG for stale/filtered), and prefer reusing the existing DropKinds — DIS deliberately added none.
  • Satisfy the sequence gate. Stamp pkt.sequence = ++seq_ per accepted message so StateStore::apply's staleness check never self-fires; do your protocol's own staleness before this point.
  • Carry the satellite forward if your protocol updates entities individually: apply() replaces the satellite wholesale, so stamp the last-known satellite state into every synthesized packet.
  • Contain third-party types. Decoder library includes and types stay inside the .cpp; wrap decode calls in try/catch and convert exceptions to malformed drops (the open-dis pattern).

4. Wire the mode switch and configuration

  1. input_source.hpp/cpp: add InputMode::kFoo, extend parseInputMode/toString, and add the case to makeInputSource().
  2. config.hpp: add FooInputConfig foo; to Config.
  3. config.cpp — strict schema: flat keys under [input] (the TOML subset has one table level — follow the dis_* prefix convention): 
    // in applyConfigFile(): every key gets a type check AND a range check
} else if (key == "input.foo_port") {
  if (!requireInt(v, err)) return false;
  if (v.i < 1 || v.i > 65535) return fail(err, key, line, "out of range");
  cfg.foo.port = static_cast<int>(v.i);
}
    Keys must be schema-checked whenever present, even if mode != "foo" (the DIS keys behave this way). Add cross-field invariants on the merged config (e.g. "mode=foo requires foo_whatever") after both passes.
  4. CLI: extend --input-mode's accepted values and printUsage. Follow the DIS precedent: protocol-specific settings live in the config file only — don't grow a flag per key.
  5. Samples: add commented keys with defaults to config/backend.toml.

5. Test the interface

Cover: every drop reason, the accept path, mapping of each field, satellite identification + carry-forward, staleness (first message, newer, older, wraparound if applicable), and "synthesized sequence never self-stales". test_dis_input_source.cpp (505 lines — the exhaustive example)
Config tests Extend test_config.cpp: each new key valid / wrong type / out of range / unknown-key still rejected; mode parsing; cross-field invariant; precedence with --config. the existing dis_* cases
Emitter (optional) If the simulator learns to emit the protocol (--protocol foo): a foo_builder in olv_sim_lib + marshal unit tests + a round-trip test (emit → processDatagram → expect equivalent state). dis_builder.cpp + its tests
Integration A scenario in (or parallel to) scripts/integration_test.sh: backend in foo mode on random ports, drive it, capture frames with olv_ws_probe, re-validate with validate_message.mjs, grep the log for accepted/connected. the existing script
Regression Prove the default path is untouched: full existing suite green unmodified, and a default-config run's startup log line byte-identical to before your change. the DIS feature's Phase-5 acceptance

6. If the interface needs a third-party decoder

Follow the open-dis-cpp dependency pattern exactly — it is the repo's template for "one more compiled dependency without breaking the air gap":

  1. Pin an exact upstream version; install via a scripts/install_<lib>.sh that sha256-verifies the tarball before building, supports OLV_<LIB>_TARBALL/_URL mirrors, and installs headers + a static lib + LICENSE into a prefix.
  2. Locate it with a cmake/<lib>.cmake exposing an imported target with SYSTEM headers; search the standard prefixes plus a -DOLV_<LIB>_PREFIX override; FATAL_ERROR with install instructions when missing.
  3. Run the installer in the Containerfile's build stage (before COPY . ., for layer caching) and document the air-gap build args.
  4. Update THIRD_PARTY.md, scripts/gen_sbom.py (new component + pinned version), and regenerate sbom/.

7. Output interfaces (new consumers)

Adding a new output (say, a REST snapshot endpoint or a second broadcast format) has a smaller but analogous shape:

  • Read state only via StateStore::snapshot() — never hold the mutex across serialization or I/O.
  • Run on the existing main-thread io_context (like WsServer) unless you have a measured reason for another thread; if you do add one, it must not touch the WS sessions.
  • Serialize once per tick and share the buffer (shared_ptr<const string>) if fanning out; bound per-consumer queues and drop data, not connections, under back-pressure (the 5-frame outbox precedent).
  • Spec the format normatively (a docs/PROTOCOL_*.md with a sample message and field table, like PROTOCOL_WS.md), version it explicitly, and give the integration test a capture-and-validate path for it.

8. Ship checklist

  1. ☐ docs/PROTOCOL_<NAME>.md (normative) + docs/features/FEATURE_<NAME>.md (design record)
  2. ☐ FooInputSource with private io thread, three-call contract, all-or-nothing drops, public processDatagram seam
  3. ☐ InputMode + factory + strict config keys + cross-field invariants + sample TOML + usage text
  4. ☐ Unit tests (pipeline + config), optional emitter + round-trip, integration scenario
  5. ☐ Existing suite green unmodified; default startup log byte-identical
  6. ☐ Dependency plumbing (installer, cmake module, Containerfile, THIRD_PARTY.md, SBOM) if applicable
  7. ☐ README: build/run snippet + port table entry; this doc site's CLI/config references
