Extending the Software

Recipes for the most likely extensions, each following the project's established patterns. General rule: update the normative doc, the code, and the tests together — the docs in docs/ are specs, not descriptions.

Add a new input source (e.g. another protocol)

This is the designed-for extension — DIS was added exactly this way (docs/features/FEATURE_INPUT_SOURCES.md is the worked example). The condensed steps are below; the complete procedure — spec template, code skeleton, dependency plumbing, test matrix, and ship checklist — has its own page: Adding a New Interface.

  1. Create backend/src/foo_input_source.{hpp,cpp} implementing InputSource: own a private io_context, socket, and thread; make start()/stop() idempotent.
  2. Feed the store only through countReceived, countDropped, apply — this keeps the Stats panel truthful with zero frontend changes. Synthesize a strictly-increasing sequence if your protocol lacks one (see DisInputSource).
  3. Expose a processDatagram()-style public test seam and write unit tests that drive it with crafted byte arrays.
  4. Extend InputMode, parseInputMode, and makeInputSource() in input_source.{hpp,cpp}; add config keys under [input] in config.cpp (flat foo_* keys — the TOML subset has one table level) with strict type/range checks; add cross-field invariants on the merged config.
  5. Write docs/PROTOCOL_FOO.md (accepted subset, mapping, validation order, stats identity) and add the commented keys to config/backend.toml.
  6. Verify the default path is untouched: the pre-existing tests must pass unmodified, and a default-config run should produce a byte-identical startup log line (the DIS feature held itself to exactly this bar).

Add a new object category

Touches every layer, in this order:

  1. Protocol: new ObjectType value in protocol.hpp + isKnownObjectType/toString; bump nothing (new enum values under version 1 are additive for senders, but old receivers will reject them — coordinate deployment). Update docs/PROTOCOL_UDP.md §3.
  2. Backend: nothing else — the backend treats types opaquely.
  3. Simulator: csv_reader.cpp name mapping, generator.cpp mix (if desired), dis_builder.cpp EntityType mapping.
  4. Frontend: net.js category map; renderer.js CAT table (color/size/icon — add an atlas cell in atlas.js and extend its frozen-constant test); ui.js/index.html filter chip + settings checkbox; settings.js DEFAULTS.categories.
  5. Tests: protocol round-trip, CSV parse, net.js category test, atlas determinism test.

Add a configuration option

  • Backend/simulator: add the field to the config struct with its default; add the key to applyConfigFile (type + range check, keep the strict unknown-key rejection working); if it needs a CLI flag, add it to parseArgs pass 2 and printUsage; document it in the sample TOML and add cases to test_config.cpp (valid, wrong type, out of range, precedence).
  • Frontend user setting: add to DEFAULTS in settings.js with validation/clamping in applyPatch; add the control to the Settings modal in index.html + sync/wiring in ui.js; consume it in main.js's applyRendererSettings (and renderer.normalizeSettings). Existing localStorage blobs lack the key — your default must apply cleanly (no migration needed if you follow the coerce-with-default pattern).
  • Frontend site default: additionally add the key to SITE_CONFIG_SCHEMA in site_config.js and the commented example in frontend/config.toml. Remember the lenient contract: invalid values warn and fall back, never throw.

Add a UI panel or renderer feature

  1. Markup in index.html; wiring in ui.js (follow the existing panel pattern: an updateData(model) hook + a 1 s tick() for relative times).
  2. Renderer features: keep new draw code inside renderer.js; reuse the four existing GLSL programs where possible (the sky feature added stars, Moon, and planets with zero shader changes — atlas cells + existing point/marker paths). If you must touch a vertex shader, remember every VS carries the fisheye branch — test in both view modes.
  3. Anything mathematical goes in a new pure module (like sky.js) so it gets Node tests without a browser.
  4. Write a frozen-interface feature doc in docs/features/ first if the change is nontrivial — that's the repo's established process (SATVIEW and SKY are the templates).

Add a CLI tool

Follow backend/tools/ws_probe.cpp: a single file under tools/, linking only what it needs (the probe deliberately links Boost only, not olv_core, to stay an independent check). Add an add_executable in the subproject CMakeLists and, if test-support, wire it into scripts/integration_test.sh via a target-file argument in the top-level CTest registration.

Add unit tests

  • C++: new test_foo.cpp in backend/tests/ or simulator/tests/; include olv_test.hpp, write OLV_TEST(...) cases, and add the file to the test binary's source list in CMakeLists. Do not add OLV_TEST_MAIN() — exactly one file per binary has it (test_protocol.cpp / the sim equivalent).
  • Frontend: new frontend/tests/foo.test.mjs using node:test; import the pure module directly. Keep modules import-safe (no DOM access at import time) or they can't be tested this way — that constraint is why main.js/ui.js isolate all DOM handling.

Extend the integration test

scripts/integration_test.sh is plain bash: ephemeral random ports, a temp dir, a cleanup trap. To add a scenario (e.g. DIS end-to-end), follow its existing steps — start backend with a written config, drive with olv_sim, capture with olv_ws_probe, assert on frames and the backend log. Keep the whole run under the 120 s CTest timeout and preserve the "random ports, no fixed state" discipline so parallel CI runs don't collide.

Evolve the OLV1 protocol itself

  • Additive message types: allowed under version 1 — receivers reject unknown msg_type, so ship receiver support first.
  • Any layout change: bump kVersion; old receivers will reject new packets (kBadVersion) — coordinate rollout.
  • Always change protocol.hpp, docs/PROTOCOL_UDP.md, test_protocol.cpp/test_validation.cpp, and the frontend parser together; the integration test's frame-revalidation step is your cross-component safety net.
The invariants to never break: (1) drops are all-or-nothing — never partially apply a packet; (2) every drop is counted and logged with a reason; (3) thread 1 writes state only via the three StateStore methods; (4) the GLSL fisheye block and sat_camera.js stay in lockstep; (5) backend/simulator config stays strict, frontend config stays lenient.
