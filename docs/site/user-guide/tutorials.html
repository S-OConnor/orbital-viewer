Tutorials

Guided scenarios from beginner to advanced. Each assumes a built repo (Installation) and starts from a clean state.

Tutorial 1 (beginner): the containerized demo, explored

  1. Start: scripts/run_all.sh and open http://localhost:8000/.
  2. In the Objects panel, click the debris chip — the list filters to debris only; chips show live per-category counts.
  3. Click a debris row. Find its ring on the globe; open Settings, enable Show trails, and watch its path build up (the example mission loops every 61 seconds).
  4. Press V. You are now looking straight down from the satellite through a 170° fisheye; Earth's limb is the bright circle. Press V again.
  5. In the terminal, press Ctrl-C once — containers stop and remove themselves. Confirm with podman ps (empty).

Tutorial 2 (beginner): author and replay your own mission

  1. Create mymission.csv — a satellite pass plus one highlighted debris object and one ground-hot source: 
    time_s,kind,id,type,px_m,py_m,pz_m,vx_mps,vy_mps,vz_mps,confidence,intensity,flags
0,sat,1,,6921000,0,0,0,7600,0,,,
0,obj,101,debris,6921000,50000,0,0,7500,100,90,0,2
0,obj,201,ground_hot,1113195,-4842330,3985029,,,,95,1450,0
1,sat,1,,6920958,7600,0,-8.3,7600,0,,,
1,obj,101,debris,6920959,57500,100,-8.3,7500,100,90,0,2
    Notes: type accepts names (debris, star, comet, satellite, ground_hot) or numbers 1–5; empty velocity triple means "no velocity"; flags=2 sets HIGHLIGHT; the header line must match exactly.
  2. Run the backend, then replay: 
    ./build/tools/simulator/olv_sim --csv mymission.csv --rate 1 --loop
  3. In the viewer: object 101 renders highlighted; 201 sits on Earth's surface, tinted by its 1450 K intensity. The satellite panel tracks id 1.
  4. Malformed-input experiment: change a row's type to 7 and rerun — the simulator rejects the CSV with the line number. Validation starts before the wire.

Tutorial 3 (intermediate): remote backend on a LAN

Goal: backend + simulator on host A (e.g. 192.168.1.20), browser on host B.

  1. Host A: open the firewall and start the backend bound to all interfaces (the default): 
    sudo firewall-cmd --add-port=47000/udp --add-port=8765/tcp --add-port=8000/tcp
./build/olv_backend --log-file olv.log
./build/tools/simulator/olv_sim --generate 800 --duration 0 &
scripts/serve_frontend.sh 8000
  2. Host B: browse to http://192.168.1.20:8000/frontend/. The frontend defaults its WebSocket host to the page's hostname, so it connects to ws://192.168.1.20:8765/ automatically — no settings needed.
  3. Verify on host A: olv.log shows a client connected line with host B's address; the Stats panel on B shows WS clients counting every open tab.

Tutorial 4 (intermediate): capacity load test with live stats

  1. Start the backend with debug logging: ./build/olv_backend --log-level debug --log-file load.log
  2. Drive it at the protocol ceiling: 
    ./build/tools/simulator/olv_sim --generate 5000 --rate 1 --duration 300
    5,000 objects means each cycle is split into 40 packets (128 objects max per packet), so expect the Stats panel's UDP rate to read ~40 packets/s.
  3. While it runs: toggle trails (heaviest render path), switch to SAT view, and filter categories. The object list shows "showing 1000 of 5000" — a display cap, not data loss.
  4. Afterwards, quantify the run: 
    grep -c "accepted seq" load.log     # ~12000 accepted packets over 300 s
grep -c "dropped" load.log          # expect 0

Tutorial 5 (advanced): end-to-end DIS, and observing its lossy mapping

  1. Enable DIS in config/backend.toml: 
    [input]
mode = "dis"
dis_port = 47001
dis_satellite_entity_id = "1:1:1"
  2. Start both ends: 
    ./build/olv_backend --config config/backend.toml --log-level debug --log-file dis.log
./build/tools/simulator/olv_sim --generate 50 --protocol dis --duration 120
    (With --protocol dis and no --port, the simulator targets 47001 automatically.)
  3. Observe the documented DIS losses in the viewer: every object shows confidence 100 and intensity 0; there are no star-category objects (DIS cannot express them — they arrive as debris); object ids are FNV-1a folds of the DIS EntityID rather than the generator's raw ids.
  4. Exercise filtering: add dis_exercise_id = 2 to the backend config and restart. The simulator (emitting exercise 1 by default) is now filtered: dis.log fills with filtered exercise=1 debug lines, Stats shows received climbing while accepted stays flat. Remove the filter to recover.
  5. Cross-check stats identity: in DIS mode received ≥ accepted + dropped (filtered/ignored PDUs are neither accepted nor dropped) — visible directly in the Stats panel.

Tutorial 6 (advanced): scripted capture & validation pipeline

Build a small CI-style check that proves the whole pipeline is healthy — the same technique scripts/integration_test.sh uses:

#!/usr/bin/env bash
set -euo pipefail
./build/olv_backend --udp-port 47555 --ws-port 18765 \
    --log-file /tmp/check.log --quiet & BACKEND=$!
trap 'kill $BACKEND' EXIT
sleep 1
./build/tools/simulator/olv_sim --generate 500 --port 47555 --rate 2 --duration 20 --quiet &
./build/olv_ws_probe --host 127.0.0.1 --port 18765 \
    --count 6 --timeout 30 --out /tmp/frames.jsonl
node frontend/tests/validate_message.mjs /tmp/frames.jsonl --min-objects 100
grep -q "client connected" /tmp/check.log
echo "PIPELINE OK"

Every stage exercises a different contract: the probe checks the WS server, the validator re-parses frames with the real frontend parser, and the log grep confirms the backend's audit trail. For the full production version of this flow, read scripts/integration_test.sh.
