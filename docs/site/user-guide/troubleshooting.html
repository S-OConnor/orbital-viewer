Troubleshooting

Symptoms, causes, and fixes — build problems first, then runtime, then display. The backend log (default olv_backend.log) is the primary diagnostic tool throughout.

Where the logs are

ComponentLocationNotes
Backendolv_backend.log (or --log-file; container: /tmp/olv_backend.log inside the backend container) One line per event: <ISO-8601 ms> LEVEL [component] message. Info+ lines also mirror to stderr unless --quiet. Set --log-level debug to log every accepted packet.
Simulatorstdout/stderr only Per-cycle progress + final done: summary; send errors always print.
FrontendBrowser DevTools console Config warnings, WebSocket errors, parse-error counts.

Build-time problems

These almost never come up with the supported workflow (build inside the olv-builder container — see Installation), since Boost and open-dis-cpp are already installed in that image. The two entries below only apply if you're doing a native/advanced build.

Could NOT find Boost (native build only)

Common on immutable distros with Homebrew/Linuxbrew-installed Boost:

cmake -S . -B build -DCMAKE_PREFIX_PATH=$(brew --prefix)

The top-level CMakeLists.txt auto-adds $HOMEBREW_PREFIX and /home/linuxbrew/.linuxbrew to the prefix path, so this is usually only needed for nonstandard Homebrew locations. Boost is found in CONFIG mode; very old Boost packages without CMake config files won't work — use ≥ 1.74.

open-dis-cpp not found at configure time (native build only)

The olv-builder container image always has it (it runs it from the pinned release in containers/Dockerfile.builder). Building natively anyway and missing it, install it yourself and reconfigure — point CMake at a nonstandard prefix with -DCMAKE_PREFIX_PATH=DIR (or -DOpenDIS_DIR=DIR/lib64/cmake/OpenDIS) if it isn't in /usr/local or ~/.local (with ~/.local/bin on PATH). Air-gapped hosts: see air-gapped installation.

Weird CMake errors after moving/copying the repo

A stale build-docker/ directory with an old CMakeCache.txt from another path. Delete it and reconfigure.

Runtime problems

Backend/simulator exits immediately with a config error

Working as designed: strict config. The message names the file and the offending key — e.g. error: backend.toml: network.udp_port out of range (1-65535): 999999 — plus a line number too when the problem is TOML grammar itself (a stray array, a dotted key) rather than a schema violation. Fix the named key. Remember the TOML subset: no arrays, no dotted keys, no single quotes (grammar). For the backend, exit code 2 = bad arguments/config, exit code 1 = runtime failure (e.g. log file unwritable, port bind); the simulator always exits 1, for both kinds of failure.

bind: address already in use on 8765

Another olv_backend (or anything else) already owns the port:

ss -tlnp | grep 8765            # who owns it
scripts/cleanup.sh              # stops containerized stacks + stray processes
# or run on a different port:
./build-docker/olv_backend --ws-port 8766   # update frontend Settings to match

Simulator packets never arrive (Stats stays at 0)

  1. Confirm the simulator is pointing at the right host/port (--dest/--port vs the backend's --udp-port — and note DIS mode listens on 47001, not 47000).
  2. Check the firewall (typical on Fedora-family hosts): 
    sudo firewall-cmd --add-port=47000/udp --add-port=8765/tcp     # runtime only
sudo firewall-cmd --permanent --add-port=47000/udp --add-port=8765/tcp
sudo firewall-cmd --reload
  3. Check the log: if packets arrive but are rejected, you'll see dropped <reason> WARN lines with the sender's address — a version mismatch, wrong protocol on the port (OLV1 vs DIS), or corruption.

Stats shows drops climbing

Log reasonMeaningLikely cause
bad_magic / bad_version / bad_msg_type / too_short / too_long Not a valid OLV1 packetWrong sender/protocol pointed at the port
bad_length / bad_crc / too_many_objects Truncated, corrupted, or malformed-count datagram Network corruption; a non-OLV1 sender; IP fragmentation issues (try --chunk 24)

DIS mode: PDUs arrive but nothing displays

  • filtered exercise=N in the debug log → your dis_exercise_id filter doesn't match the traffic.
  • ignored pdu kind=N → only Entity State (type 1) PDUs are consumed; heartbeats/fire/detonation etc. are ignored by design.
  • Satellite panel empty but objects show → no entity matches dis_satellite_entity_id; check the three-part id against the exercise's actual EntityIDs.
  • dropped bad_version → source is emitting a DIS protocol version outside 5–7.

Display problems

Page loads but the globe stays empty / status "stalled"

  1. Open Settings — do host/port match a running backend? (Default: localhost:8765; "stalled" means no state frame for >3 s.)
  2. Click Reconnect. Watch the DevTools console for WebSocket errors.
  3. Confirm the backend is broadcasting: olv_ws_probe --count 1 ... (see Usage) — if the probe captures a frame, the problem is in the browser's settings/network, not the backend.
  4. Globe visible but no objects: check the category toggles in Settings and the expiry window — a paused source means objects expire after 15 s.

Blank page when opening index.html directly

ES modules are blocked from file://. Serve over HTTP: scripts/serve_frontend.sh 8000 → http://localhost:8000/frontend/.

"WebGL initialization failed" overlay

The browser couldn't create a WebGL 1 context. Check about:gpu / hardware acceleration settings, try another browser, or update GPU drivers. The app requires WebGL but degrades nothing else — the fatal overlay is the intended behavior.

Settings seem stuck or corrupted

Settings live in localStorage key olv.settings.v1. Use Reset to defaults in the Settings panel, or clear the key manually in DevTools (corrupt JSON is tolerated and falls back to defaults automatically).

Recovery procedures

  • Full stop, containers: Ctrl-C in run_all.sh, or scripts/cleanup.sh (also kills stray native processes and dev servers, and force-stops olv_* containers).
  • State reset: the backend keeps no persistent state — restarting it resets counters, sequence baseline, and the object table. The frontend's only persistence is localStorage settings.
  • Rebuild from scratch: rm -rf build-docker && docker run --rm --user "$(id -u):$(id -g)" -v "$PWD":/src -w /src localhost/olv-builder:latest sh -c 'cmake -S . -B build-docker -DCMAKE_BUILD_TYPE=Release && cmake --build build-docker -j"$(nproc)"'; containers: scripts/run_all.sh --build.
  • Sanity baseline: docker run --rm -v "$PWD":/src -w /src localhost/olv-builder:latest sh -c 'ctest --test-dir build-docker --output-on-failure' — if integration passes, the entire sim → backend → WS → parser pipeline works on this machine, and the problem is configuration or environment.
